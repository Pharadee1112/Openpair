1. Introduction
1.1 Purpose
จุดประสงค์ของโปรเจกต์ "OpenPair" คือการสร้างระบบ AI Router ที่มีความแม่นยําสูง เพื่อทําหน้าที่เป็น "จราจรทางอากาศ" (Intelligence
Layer) ให้กับข้อมูล ระบบจะทําการจําแนกงาน (Task) ที่เข้ามา แล้วเลือกใช้ AI Model หรือ Ecosystem ที่เหมาะสมที่สุดโดยอัตโนมัติ
เป้ าหมายหลักของระบบ ได้แก่:
• Cost Optimization — ลดค่าใช้จ่ายจากการเรียกใช้ Model ระดับสูงพรํ่าเพรื่อ (ประหยัดได้สูงสุดถึง 85%)
• Speed Improvement — เพิ่มความเร็วในการตอบสนองโดยกระจายงานง่ายๆ ไปยัง Model ขนาดเล็กที่ทํางานได้เร็วกว่า
• Quality Preservation — ยังคงคุณภาพของผลลัพธ์ไว้ด้วยระบบ Fallback และ LLM-as-a-Judge อัตโนมัติ
• Developer Experience — ติดตั้งและใช้งานได้ง่ายผ่าน pip install และ CLI Interface
1.2 Scope
ระบบ OpenPair จะถูกพัฒนาในรูปแบบ Hybrid Architecture โดยมีองค์ประกอบหลักดังนี้:
• Core Engine: พัฒนาด้วยภาษาประสิทธิภาพสูง (Rust หรือ Go) เพื่อความเร็วระดับมิลลิวินาที ไม่มี Garbage Collector
Overhead
• Python Binding: ใช้ PyO3 + Maturin (สําหรับ Rust) หรือ cgo (สําหรับ Go) เพื่อห่อหุ้มเป็น Python Package
• CLI Interface: รองรับการใช้งานผ่าน Terminal สําหรับนักพัฒนา
• Python Library: สามารถ import ใช้ใน codebase ได้ทันที ผ่าน pip install openpair
• Web Application (Future): รองรับการขยายเป็น REST API และ Web Dashboard ในอนาคต

3. Functional Requirements
ระบบทํางานผ่านแนวคิด Unit of Work ที่มองต้นทุน ความเร็ว และคุณภาพเป็นหลัก
3.1 Multi-Stage Classification
3.1.1 Semantic Router
ระบบต้องสามารถแปลง Prompt ที่รับเข้ามาเป็น Vector Embeddings และเทียบความคล้ายคลึงกับกลุ่มงานที่กําหนดไว้ด้วย Cosine
Similarity:
• ใช้ BERT-base หรือ Sentence-Transformers สําหรับการสร้าง Embeddings
• กําหนด Route Groups ล่วงหน้า เช่น Code, Summarization, Translation, Creative Writing, Data
Analysis, Q&A
• คํานวณ Cosine Similarity ใน Core Engine (Rust/Go) เพื่อความเร็วสูงสุด
• Threshold การจําแนก: ≥ 0.75 = High Confidence, 0.50–0.74 = Medium, < 0.50 = Fallback to LLM
Judge
3.1.2 Intent Classifier (Gatekeeper)
ระบบต้องมี Gatekeeper ที่วิเคราะห์ความซับซ้อนของงาน:
• Complexity Score 1–10: วัดจาก Prompt Length, Vocabulary Diversity, Chain-of-Thought
Requirement
• Task Type Detection: Generative vs. Extractive vs. Reasoning
• Context Requirement: ตรวจสอบว่างานต้องการ Long Context (> 16K tokens) หรือไม่
• Sensitivity Check: ตรวจสอบว่างานเกี่ยวข้องกับข้อมูลส่วนตัวหรือ Compliance ที่ต้องการ Local Model
3.2 Model Capabilities Registry
3.2.1 Dynamic Metadata Store
ระบบต้องมีฐานข้อมูล In-Memory ที่อัปเดตได้:
• เก็บข้อมูล: Model Name, Provider, Capabilities Tags, Pricing (per 1K token), Context Window,
Average Latency
• รองรับการอัปเดต Registry แบบ Hot-Reload โดยไม่ต้องรีสตาร์ทระบบ
• รองรับ Custom Model เช่น Ollama Local Models ที่ผู้ใช้กําหนดเอง
3.2.2 Constraint Checker
ก่อนส่งงานให้ Model ระบบต้องตรวจสอบ:
• Context Window: ความยาว Prompt ต้องไม่เกิน Context Limit ของ Model

3.3.2 Cost vs. Performance Framework
นําแนวคิดจากงานวิจัย FrugalGPT และ RouteLLM มาประยุกต์ใช้:
• Quality Threshold (Q): ผู้ใช้กําหนดเกณฑ์คุณภาพขั้นตํ่า (0.0 – 1.0) ระบบจะเลือก Model ที่ถูกที่สุดที่ผ่านเกณฑ์
• Cost Weight (λ): นํ้าหนักที่ให้กับต้นทุนในสูตร Score = Quality − λ × Cost
• Learned Routing: ระบบบันทึก Feedback Loop เพื่อปรับ Routing Decision ให้ดีขึ้นตามเวลา
3.4 Fallback & LLM-as-a-Judge
3.4.1 Quality Verification
• ระบบใช้ Small LLM (เช่น GPT-4o-mini) ตรวจสอบคุณภาพคําตอบจาก Model หลัก
• Verification Criteria: Factual Accuracy, Completeness, Format Compliance
• หากคะแนนตํ่ากว่า Threshold ที่กําหนด ระบบจะ Reroute อัตโนมัติ

4. Technical Implementation Specifications
4.1 Architecture: Hybrid Core & Python Binding
4.1.1 Core Engine (Rust — Recommended)
ไลร่าแนะนํา Rust เป็น Core Engine หลัก เนื่องจากข้อได้เปรียบดังนี้:
• Zero-cost abstractions: ไม่มี Runtime Overhead
• No Garbage Collector: ไม่มี Stop-the-World Pause ทําให้ Latency คาดเดาได้
• Memory Safety: Borrow Checker ป้ องกัน Memory Leak และ Data Race
• SIMD Support: ใช้ AVX2/AVX-512 สําหรับ Vector Math (Cosine Similarity) ได้โดยตรง
• PyO3 Ecosystem: การสร้าง Python Binding ที่สมบูรณ์และมี Community ขนาดใหญ่

5. Non-Functional Requirements
5.1 Performance
Metric Target Notes
Routing Decision Latency < 5 ms P99 — ไม่รวม Network Time ไปยัง Provider
Embedding Computation < 50 ms สําหรับ Prompt ขนาด 1K tokens
Memory Footprint (Core) < 100 MB ขณะ Idle, รวม Model Registry และ Embeddings
Throughput ≥ 1,000 req/sec บน Hardware 4-core, 8GB RAM
Cache Hit Rate (Target) ≥ 40% LRU Cache สําหรับ Repeated/Similar
Prompts
Cold Start Time < 500 ms เวลาโหลด Registry และ Embeddings ครั้งแรก
5.2 Reliability & Availability
• Automatic Failover: หาก Model ปลายทาง Downtime ระบบต้องสลับไปยัง Model สํารองที่มี Capability
ใกล้เคียงภายใน < 200ms
• Circuit Breaker: หาก Provider มี Error Rate > 10% ใน 60 วินาที ระบบจะหยุดส่งงานชั่วคราวและแจ้งเตือน
• Health Check: ระบบตรวจสอบ Provider API Status ทุก 30 วินาทีใน Background
• Graceful Degradation: หาก Core Engine ล้มเหลว Python Layer ต้องสามารถ Fallback ไปยัง Direct API
Call ได้
5.3 Security
• API Key Management: ไม่เก็บ API Key ใน Plain Text — ใช้ Environment Variables หรือ Secrets
Manager
• No Prompt Logging (Default): ระบบไม่บันทึกเนื้อหา Prompt ลง Log โดย Default (ป้ องกัน Data Leak)
• Local Model Support: รองรับ Ollama สําหรับ Use Case ที่ต้องการ Data Privacy สูง (ไม่ส่งข้อมูลออกนอก)
• Input Sanitization: ตรวจสอบ Prompt สําหรับ Prompt Injection Attack ก่อนส่งต่อ
5.4 Maintainability & Extensibility
• Plugin Architecture: รองรับการเพิ่ม Custom Classifier หรือ Router Strategy ผ่าน Plugin Interface
• Model Agnostic: ไม่ผูกติดกับ Provider ใด รองรับการเพิ่ม Model ใหม่ผ่าน YAML/JSON Config
• Observability: รองรับ OpenTelemetry สําหรับ Tracing และ Prometheus สําหรับ Metrics

7. Web Application Architecture (Future)
ในอนาคต OpenPair จะขยายจาก CLI/Library กลายเป็น Full-Stack Web Application ที่รองรับทีมและองค์กร:
7.1 Frontend
• Framework: React 18+ + TypeScript
• UI Library: Shadcn/UI + Tailwind CSS
• Charts: Recharts สําหรับ Cost & Routing Analytics
• State Management: Zustand หรือ TanStack Query
• Features: Dashboard, Model Registry Editor, Live Router Testing, Cost Reports
7.2 Backend API
• Framework: FastAPI (Python) — ห่อหุ้ม OpenPair Core Library
• Authentication: JWT + OAuth2 (GitHub, Google SSO)
• Database: PostgreSQL สําหรับ User Data / Usage History, Redis สําหรับ Cache
• Queue: Celery + Redis สําหรับ Async Long-running Tasks
• API Documentation: Auto-generated Swagger UI จาก FastAPI
7.3 Infrastructure
• Containerization: Docker + Docker Compose (Dev), Kubernetes (Production)
• CI/CD: GitHub Actions — Test → Build → Deploy pipeline
• Cloud: AWS (ECS/EKS) หรือ GCP (Cloud Run) — Serverless-compatible
• CDN: Cloudflare สําหรับ Frontend Assets
• Monitoring: Grafana + Prometheus + Sentry

## บทคัดย่อ

ระบบ router ที่คำนึงถึงต้นทุนจะส่ง prompt แต่ละอันไปยัง model ที่ถูกที่สุดที่ทำงานนั้นได้ แต่สัญญาณคุณภาพที่ router ใช้ตัดสินใจมักวัดจากภาษาอังกฤษ เราพัฒนา OpenPair ซึ่งเป็น router ที่ใช้เฉพาะ model ฟรีของ Gemini และ Groq และสร้างชุดทดสอบภาษาไทย 600 เคส ครอบคลุม 6 หมวดงาน (ถาม-ตอบ, แปล, สรุปความ, จัดหมวดหมู่, เขียนโค้ดในบริบทไทย, งานเขียนสร้างสรรค์) โดยใช้เนื้อหาจากข่าวเดือนกันยายน 2569, สแลงโซเชียลมีเดีย, สำนวน, ภาษาถิ่น, ระดับภาษา และการประชด เราประเมิน Gemini 3.1 Flash-Lite, gpt-oss-120b และ gpt-oss-20b บน 598 เคสที่ทั้งสาม model ตอบครบ Gemini ได้คะแนน 9.40 / 10 [95% CI 9.33–9.48] สูงกว่า gpt-oss-120b (8.79) และ gpt-oss-20b (8.71) อย่างมีนัยสำคัญ ขณะที่ gpt-oss ทั้งสองขนาดไม่ต่างกันทางสถิติ (ผลต่างแบบจับคู่ 0.09 [−0.01, 0.18]) ช่องว่างกว้างที่สุดในเคสสแลง (8.88 เทียบกับ 7.68 / 7.38) และสำนวน ซึ่ง gpt-oss ให้คำอธิบายที่ลื่นไหล มั่นใจ แต่ผิดความหมาย การให้คนไทยตรวจคำตอบ 462 คำตอบแบบ blind ยืนยันช่องว่างนี้ (คำตอบที่ตัดสินได้ถูก 100%, 76% และ 60%) และแสดงว่าตัวให้คะแนนแบบ keyword ตรงกับคนเพียง 84% นอกจากนี้เรารายงานสิ่งที่ benchmark ของเราวัดไม่ได้ด้วย ได้แก่ ป้ายความยากที่ผู้เขียนกำหนดไม่สัมพันธ์กับคะแนน (Spearman ρ ระหว่าง −0.10 ถึง −0.03), 32% ของเคสทุก model ได้คะแนนเต็ม และตัวให้คะแนนแบบ keyword ให้คะแนนคำตอบยาวที่ตอบหลายตัวเลือกมากเกินจริง เราเผยแพร่ชุดเคส ตัวให้คะแนน และสคริปต์วิเคราะห์ พร้อมเสนอแนวทางต่อยอดที่ชัดเจน

## 1. บทนำ

- ปัญหา: นักพัฒนาที่ใช้ LLM หลาย provider มักกำหนด model แพงตัวเดียวตายตัว หรือจ่ายค่า model แรงๆ กับ prompt ง่ายๆ งาน router อย่าง FrugalGPT, RouteLLM และ AutoMix แก้ปัญหาด้านต้นทุน แต่สัญญาณที่ใช้ตัดสินใจถูกเรียนรู้หรือทดสอบบน benchmark ภาษาอังกฤษ
- สำหรับภาษาไทย การมีแค่ตัวบอกว่า "model นี้ทำภาษาไทยได้" ไม่พอ model ที่ดูตอบไทยได้คล่องอาจเข้าใจสแลงหรือการประชดผิด และ router ที่ดูแค่ว่าคำตอบเป็นภาษาอะไรจะมองไม่เห็นความผิดพลาดนี้
- ข้อจำกัดที่กำหนดรูปแบบงานนี้: ใช้ได้เฉพาะ API ฟรี (Gemini, Groq) และ GPU ทั่วไปขนาด 4 GB ซึ่งเป็นสภาพจริงของนักศึกษาและทีมเล็กๆ ในประเทศไทย และจำกัดว่าเราทดสอบได้กี่ model และกี่รอบ
- สิ่งที่งานนี้นำเสนอ:
  1. ชุดทดสอบภาษาไทย 600 เคส (หมวดละ 100) พร้อมป้ายประเภทเนื้อหา (สแลง, ข่าวปัจจุบัน, สำนวน, ภาษาถิ่น, ระดับภาษา, การประชด, การตรวจจับข้อความหลอกลวง)
  2. การเปรียบเทียบพฤติกรรมของ model ฟรี 3 ตัว พร้อม bootstrap CI และการทดสอบแบบจับคู่ แยกตามหมวด ประเภทเนื้อหา และความยาก
  3. การรายงานข้อจำกัดของ benchmark อย่างตรงไปตรงมา (คะแนนชนเพดาน, ความน่าเชื่อถือของป้ายความยาก, ความลำเอียงของตัวให้คะแนน) และจุดอ่อนของ model เขียนเป็นแนวทางให้นักวิจัยที่จะทำต่อ
  4. OpenPair router แบบ open-source (แกนหลักเป็น Rust ห่อด้วย Python) ซึ่งตาราง routing ภาษาไทยตั้งจากผลการวัดนี้
- ขอบเขต: งานนี้เป็นการศึกษาเชิงวัดผล คำถามวิจัยคือ model พลาดตรงไหนในภาษาไทย ไม่ใช่จะทำให้ model เก่งขึ้นอย่างไร การเทรน model (เช่น fine-tuning) จึงอยู่นอกขอบเขตของ paper นี้โดยตั้งใจ หัวข้อ 8 อธิบายว่าจุดที่ model พลาดซึ่งพบในงานนี้ใช้เป็นเป้าหมายของงานแบบนั้นได้อย่างไร

## 2. งานวิจัยที่เกี่ยวข้อง

**การ routing และ cascade แบบคำนึงถึงต้นทุน** FrugalGPT (Chen, Zaharia & Zou, 2023 / TMLR 2024) มองการลดต้นทุน LLM เป็นสามแนวทาง ได้แก่ การปรับ prompt, การประมาณ model และ cascade แล้วเรียนรู้ว่าควรเรียก model ชุดไหนสำหรับแต่ละ input รายงานว่าลดต้นทุนได้ถึง 98% โดยแม่นยำระดับ GPT-4 ส่วน RouteLLM (Ong et al., ICLR 2025) ฝึก router เลือกระหว่าง model แรงกับ model ถูก จากข้อมูลความชอบของมนุษย์ รายงานว่าประหยัดได้มากกว่า 2 เท่าโดยคุณภาพไม่ลด และ router ใช้กับ model คู่ใหม่ที่ไม่เคยเห็นได้ ส่วน AutoMix (Aggarwal, Madaan et al., NeurIPS 2024) ส่งงานต่อไป model ใหญ่ตามผลการตรวจตัวเองแบบ few-shot ของ model เล็ก โดยมี meta-verifier คอยแก้ผลตรวจตัวเองที่คลาดเคลื่อน ทั้งสามงานเรียนรู้หรือทดสอบสัญญาณ routing บนงานภาษาอังกฤษ OpenPair เรียบง่ายกว่ามาก คือใช้คะแนนความซับซ้อนแบบกฎ (rule-based) บวกกับคะแนนภาษาไทยที่วัดจริงของแต่ละ model และสิ่งที่งานนี้นำเสนอไม่ใช่ตัว router แต่เป็นหลักฐานว่าสัญญาณภาษาไทยแบบนี้ควรและไม่ควรวัดอะไร

**การประเมินภาษาไทยและภาษาในเอเชียตะวันออกเฉียงใต้** Typhoon (Pipatanakul et al., 2023) เสนอ ThaiExam ที่สร้างจากข้อสอบระดับชาติและข้อสอบวิชาชีพของไทย (O-NET, IC และต่อมาเพิ่ม TGAT, TPAT-1, A-Level) ปัจจุบันมี leaderboard บน HELM ส่วน Typhoon 2 (Pipatanakul et al., 2024) และ Thai LLM Leaderboard (SCB 10X, VISTEC, SEACrowd) เพิ่ม Thai MT-Bench ที่ใช้ LLM เป็นผู้ตัดสิน SEA-HELM (Susanto et al., 2025) ประเมินภาษาไทยร่วมกับอีก 4 ภาษาในภูมิภาค ครอบคลุมงาน NLP พื้นฐาน, ความสามารถเฉพาะของ LLM, ภาษาศาสตร์, วัฒนธรรม และความปลอดภัย Limkonchotiwat et al. (2025) ประเมินความสามารถด้านภาษาถิ่นไทยด้วย benchmark อัตโนมัติร่วมกับการประเมินโดยคน benchmark เหล่านี้เน้นความรู้แบบข้อสอบหรือการทำตามคำสั่งทั่วไป ส่วนของเราเจาะเนื้อหาที่เปลี่ยนเร็วที่สุดและ router มีโอกาสเคยเห็นน้อยที่สุด คือสแลง ระดับภาษาบนโซเชียล และข่าวของเดือนที่ทดสอบ และออกแบบให้ถูกพอจะรันซ้ำได้บน API ฟรี

**การประเมินอัตโนมัติและความลำเอียง** Zheng et al. (2023) แสดงว่า LLM ที่เก่งเมื่อใช้เป็นผู้ตัดสินจะเห็นตรงกับมนุษย์บ่อยพอๆ กับที่มนุษย์เห็นตรงกันเอง แต่ก็พบความลำเอียงด้านตำแหน่ง (position bias) และความยาว (verbosity bias) เราตั้งใจไม่ใช้ LLM เป็นผู้ตัดสิน (เพราะต้นทุน และผู้ตัดสินเองก็จะเป็นหนึ่งใน model ที่ถูกศึกษา) แต่ใช้การจับ keyword แทน ซึ่งหัวข้อ 7 แสดงว่าตัวให้คะแนนของเราก็มีความลำเอียงด้านความยาวเช่นกัน

**Hallucination** Huang et al. (2023) แบ่ง hallucination เป็นแบบขัดกับข้อเท็จจริงของโลก (factuality) และแบบขัดกับ input ที่ได้รับ (faithfulness) คำอธิบายความหมายสแลงที่มั่นใจแต่ผิดในหัวข้อ 6 คือ factuality hallucination ในความรู้เฉพาะวัฒนธรรม

## 3. ระบบ: OpenPair

- แกนหลัก Rust (`classifier.rs`, `router.rs`, `registry.rs`) ให้คะแนนความซับซ้อนของ prompt 1–10 ตรวจว่าเป็นภาษาไทยไหม แล้วเลือก model ที่ถูกที่สุดใน tier ที่ต้องการ ฝั่ง Python (`client.py`, `caller.py`) เรียก provider และสลับไป provider ถัดไปเมื่อเจอ 429/503 โดยด่านสุดท้ายคือ model ในเครื่องผ่าน Ollama
- ตั้งแต่ 2026-10-02 registry มีเฉพาะ model ฟรี (Gemini + Groq)
- ตาราง routing ภาษาไทยตั้งจากผลในหัวข้อ 5: ก่อนการศึกษานี้ prompt ไทยถูกส่งไป `gemini-3.1-flash-lite` (ง่าย), `gpt-oss-20b` (กลาง) และ `gpt-oss-120b` (ยาก) โดยสมมติว่า model ใหญ่กว่าจะทำภาษาไทยที่ยากกว่าได้ดีกว่า แต่หัวข้อ 5 แสดงว่า Gemini Flash-Lite ชนะ gpt-oss ทั้งสองตัวทุกระดับความยาก และ 120b ไม่ได้ดีกว่า 20b ปัจจุบัน OpenPair จึงส่ง **prompt ภาษาไทยทุกระดับไปที่ `gemini-3.1-flash-lite`** โดย gpt-oss บน Groq ยังเป็นตัวสำรองเมื่อ Gemini โดน rate limit นี่คือผลเชิงปฏิบัติโดยตรงของงานนี้: สัญชาตญาณว่า "model ใหญ่สำหรับงานยาก" ใช้ไม่ได้กับภาษาไทยในชุดนี้

## 4. ชุดทดสอบและวิธีการ

### 4.1 เคสทดสอบ
- 600 เคส หมวดละ 100 ประกอบด้วยเคส "core" 20 เคสจากชุดเดิม และเคสที่เพิ่มในเดือนกันยายน 2569 อีก 580 เคส
- ประเภทเนื้อหา (จาก notes ของแต่ละเคส หนึ่งเคสอยู่กลุ่มเดียว): สแลง/โซเชียลมีเดีย 112, ข่าวปัจจุบัน (ก.ย. 2569 ใส่เนื้อข่าวไว้ในโจทย์) 140, สำนวน/สุภาษิต 18, ภาษาถิ่น 3, ระดับภาษา 15, ประชด/ความรู้สึกผสม 6, ตรวจจับข้อความหลอกลวง 15, อื่นๆ 289 (นับจาก 598 เคสที่วิเคราะห์)
- แต่ละเคสมี prompt, keyword ที่คาดหวัง, เกณฑ์ keyword, สัดส่วนอักษรไทยขั้นต่ำ, ความยาวขั้นต่ำ และระดับความยากที่ผู้เขียนกำหนด (ง่าย 164 / กลาง 300 / ยาก 134)

### 4.2 Model และการรัน
- `gemini-3.1-flash-lite` (Google AI Studio แบบฟรี รันวันที่ 2026-10-01), `openai/gpt-oss-120b` และ `openai/gpt-oss-20b` (Groq แบบฟรี รันวันที่ 2026-10-02 เป็น model แบบ open-weight สถาปัตยกรรม MoE, OpenAI 2025)
- รัน model ละ 1 รอบ ใช้ temperature ค่าเริ่มต้นของ provider และ `max_tokens` 2048 gpt-oss-20b ได้คำตอบว่าง 2 เคสแม้ลองซ้ำ เราจึงวิเคราะห์เฉพาะ 598 เคสที่ทุก model ตอบครบ
- ไม่ได้รวม: `gemini-3.6-flash` (quota ฟรีน้อยเกินกว่าจะรัน 600 เคส รันได้แค่ชุด core 20 เคส ได้ 5.74), `gemini-3.1-pro-preview` (quota ฟรีเป็น 0) ส่วน `qwen2.5:3b` ที่รันในเครื่องผ่าน Ollama ได้ 8.10 บนชุด core 20 เคสเท่านั้น จึงรายงานในฐานะ model สำรอง ไม่ได้นำมาเปรียบเทียบ

### 4.3 การให้คะแนน
- `คะแนนรวม = 5 × สัดส่วน keyword ที่พบ + min(10 × สัดส่วนอักษรไทย, 3) + 2 × ความยาวพอ` (0–10) เคสผ่านเกณฑ์เมื่อสัดส่วน keyword ≥ เกณฑ์ สัดส่วนอักษรไทย ≥ ขั้นต่ำ และความยาวพอ
- ไม่ใช้ LLM เป็นผู้ตัดสิน การตรวจโดยคนสำหรับเคสสแลง/สำนวน/ระดับภาษา/ประชด: คนไทยตรวจครบทั้ง 154 เคส (462 คำตอบ) ตรวจและยืนยันแล้วว่าเฉลยของ 93 เคสสแลงชุดแรกถูกต้อง และยอมรับเฉลยของอีก 61 เคสตามผลตรวจชุดแรก (ไม่ได้ตรวจทีละเคส ดูข้อจำกัด) แต่ละคำตอบถูกตัดสินเป็น ถูก (Y) ผิด (N) หรือตัดสินไม่ได้ (?) แบบ blind คือ 1 บรรทัดต่อ 1 คำตอบ ซ่อนชื่อ model และคะแนนจากเครื่อง และสลับลำดับคำตอบในแต่ละข้อ (`scripts/review_simple.py`)
- สถิติ: bootstrap 95% CI (สุ่มซ้ำ 5,000 รอบ, seed 20261013), ผลต่างแบบจับคู่บนเคสเดียวกัน, Spearman ρ สำหรับความยาก

ผลต่างแบบจับคู่: Gemini − 120b = 0.61 [0.51, 0.71] (ชนะ/เสมอ/แพ้ 231/309/58), Gemini − 20b = 0.70 [0.59, 0.80], 120b − 20b = 0.09 [−0.01, 0.18] **model gpt-oss ที่ใหญ่กว่า 6 เท่าไม่ได้ให้คุณภาพภาษาไทยที่ดีขึ้นอย่างวัดได้ในชุดนี้** (พารามิเตอร์รวม 117B เทียบกับ 21B, ส่วนที่ทำงานจริง 5.1B เทียบกับ 3.6B)

### 5.2 แยกตามหมวด (รูปที่ 1)
Gemini นำทุกหมวด ช่องว่างกว้างที่สุดในหมวดถาม-ตอบ (9.35 เทียบกับ 8.12 / 8.00) และแปล (9.22 เทียบกับ 8.29 / 7.93) แคบที่สุดในหมวดจัดหมวดหมู่ (9.89 เทียบกับ 9.65 / 9.55) หมวดเดียวที่ gpt-oss ตัวเล็กชนะตัวใหญ่คือ code_thai โดย 20b (9.15) ชนะ 120b (8.84)

### 5.3 แยกตามประเภทเนื้อหา (รูปที่ 2)
สแลงเป็นเนื้อหาที่ยากที่สุดสำหรับทุก model (Gemini 8.88, 120b 7.68, 20b 7.38) ตามด้วยสำนวน (9.35 / 8.08 / 7.75) ข่าวปัจจุบันซึ่งมีข้อเท็จจริงที่ต้องใช้อยู่ในโจทย์ง่ายสำหรับทุก model (9.69 / 9.15 / 8.98) การตรวจจับข้อความหลอกลวงทั้งสาม model ได้เต็ม ภาษาถิ่น (n = 3) และการประชด (n = 6) มีจำนวนน้อยเกินกว่าจะสรุปได้

**การตีความ** เมื่อคำตอบอยู่ในบริบทที่ให้ไป model ทำได้ใกล้เคียงกัน แต่เมื่อคำตอบต้องอาศัยความรู้เฉพาะวัฒนธรรมที่โจทย์ไม่ได้ให้ไว้ model จะห่างกันมาก นี่คือความรู้ที่ "คะแนนภาษาไทย" ของ router ควรวัด และการตรวจแค่ว่าเป็นภาษาอะไรจับไม่ได้

### 5.4 เสียคะแนนจากส่วนไหน
คะแนนที่เสียเกือบทั้งหมดมาจาก keyword: Gemini เสียเฉลี่ย 0.60 ต่อเคส, 120b 1.20, 20b 1.28 ส่วนสัดส่วนภาษาไทยและความยาวเสียไม่เกิน 0.01 ตัวให้คะแนนจึงวัดเนื้อหาเป็นหลัก ไม่ได้วัดภาษา

### 5.5 ผลตรวจโดยคน (462 คำตอบ, blind)

ตรวจจากคำตอบ 80 ตัวอักษรแรกที่บันทึกไว้ คำตอบที่ตัดสินไม่ได้ (`?` ถูกตัดก่อนถึงความหมาย) ไม่นับในอัตรา

| Model | ถูก | ผิด | ตัดสินไม่ได้ | อัตราถูก |
|---|---:|---:|---:|---:|
| Gemini 3.1 Flash-Lite | 88 | 0 | 66 | 100% (88/88) |
| gpt-oss-120b | 92 | 29 | 33 | 76% (92/121) |
| gpt-oss-20b | 75 | 49 | 30 | 60% (75/124) |

แยกตามหมวด gpt-oss ใกล้เคียง Gemini ในงานจัดหมวดหมู่ (91% ทั้งคู่ เทียบกับ 100%) แต่ห่างมากในการอธิบายสแลง (67% / 50%), การแปล (76% / 45%) และงานเขียนที่ใช้สแลง (36% / 23%) และต่างจากคะแนน keyword ตรงที่ **การตรวจโดยคนแยก gpt-oss สองขนาดออกจากกันได้** (76% เทียบกับ 60%)

**ตัวให้คะแนนแบบ keyword เทียบกับคน** จาก 333 คำตอบที่ตัดสินได้ ผลผ่าน/ไม่ผ่านของเครื่องตรงกับคน 84% มี 31 คำตอบที่เครื่องให้ผ่านแต่คนบอกว่าผิด บางคำตอบได้เต็ม 10.0 ทั้งที่แปลสำนวนตรงตัว (`tr_21` "Actions speak louder than words", `tr_24` "call it a day") และได้ 9.0 ทั้งที่เขียนบทสนทนาภาษาใต้เป็นภาษาอีสาน (`cre_92`) คำตอบที่ผิดยังได้คะแนนเฉลี่ย 6.33 / 10 เทียบกับ 8.96 ของคำตอบที่ถูก ตัวให้คะแนนจึงเรียงลำดับ model ถูก แต่ประเมิน model ที่อ่อนกว่าสูงเกินจริง

**ข้อควรระวัง** คำตอบของ Gemini ตัดสินไม่ได้บ่อยกว่า (66 เทียบกับ 30–33) เพราะมักขึ้นต้นด้วยคำเกริ่น ("เลือกใช้ได้ตามสไตล์…") จนเต็ม 80 ตัวอักษร ตัวเลข 100% ของ Gemini จึงวัดจากคำตอบที่ตรงประเด็นกว่าเท่านั้น

## 6. จุดอ่อนของ model (เชิงคุณภาพ)

ตัวอย่างยกมาจากคำตอบ 80 ตัวอักษรแรกที่บันทึกไว้ ซึ่งเป็นข้อความเดียวกับที่ผู้ตรวจใช้ตัดสิน (หัวข้อ 5.5)

1. **อธิบายความหมายสแลงผิดอย่างมั่นใจ (gpt-oss)** เช่น `qa_50` "ทัวร์ลง" (การรุมวิจารณ์ออนไลน์) ที่ 120b อธิบายว่า "ลงมือทำอะไรสักอย่าง", `qa_65` "CF" ในไลฟ์ขายของ (ยืนยันการสั่งซื้อ) ที่ 20b อธิบายว่า "Cash Flow", `qa_48` "ชิป" ที่ 20b บอกว่ามาจากคำอังกฤษ "cheap" คำตอบเหล่านี้ลื่นไหล มีโครงสร้าง และเป็นภาษาไทย ไม่มีอะไรในรูปแบบคำตอบที่บอกว่าผิด ในเคสถาม-ตอบสแลง/สำนวน 39 เคส ผู้ตรวจตัดสินว่าผิด 8 จาก 24 คำตอบที่ตัดสินได้ของ 120b และ 11 จาก 22 ของ 20b ส่วน Gemini ไม่ผิดเลยจาก 28
2. **แต่งคำขึ้นเองหรือแปลสแลงตรงตัว (gpt-oss)** คำแปลที่ผู้ตรวจตัดสินว่าผิด: 10 จาก 41 (120b) และ 24 จาก 44 (20b) ที่พบบ่อยคือแปลตรงตัว (`tr_61` "slaps" → "ตบ", `tr_69` "flexing" → "แสดง"), คำที่ไม่มีอยู่จริง (`tr_77` "กรีกออกไป", `tr_80` "แซงซี่") และใช้คำทับศัพท์ผิดความหมาย (`tr_68` "MC" ซึ่งภาษาไทยแปลว่าพิธีกร)
3. **จับการประชดไม่ได้** `cls_14`, `cls_23`, `cls_26`: gpt-oss จัดข้อความบ่นแบบประชดเป็นความรู้สึกบวก เพราะตีความคำชมตามตัวอักษร
4. **ตอบงานโค้ดเป็นภาษาอังกฤษ** คำตอบหมวด code_thai ที่สัดส่วนภาษาไทย < 50%: 19 (Gemini), 70 (120b), 79 (20b) จาก 99 เคส gpt-oss เขียนคำอธิบายรอบโค้ดเป็นภาษาอังกฤษแม้ถูกถามเป็นภาษาไทย และตัวให้คะแนนแทบไม่หักคะแนนส่วนนี้ (คะแนนภาษาไทยเต็มตั้งแต่ 30%)
5. **รูปแบบคำตอบเกินจำเป็น** gpt-oss มักตอบเป็นตาราง markdown แม้เป็นคำถามสั้นหรือสำนวน (`qa_69`, `sum_96`) ไม่กระทบคะแนน keyword แต่มีผลกับหน้าจอแชต
6. **คำตอบว่าง** gpt-oss-20b ตอบว่าง 2 จาก 600 เคสทุกครั้งที่ลอง

## 7. ข้อจำกัดของวิธีการ

1. **การให้คะแนนด้วย keyword** คำพ้องความหมายไม่ได้คะแนน (`cls_50`: "พลังงาน" เทียบกับเฉลย "เทคโนโลยี" ซึ่งแก้หลังรันแล้ว) คำตอบที่ให้หลายตัวเลือกได้ keyword มากกว่า เป็นความลำเอียงด้านความยาวแบบเดียวกับที่ Zheng et al. พบใน LLM ผู้ตัดสิน
2. **คะแนนชนเพดาน** 193 เคส (32%) ทุก model ได้เต็ม และ 227 เคส (38%) ทั้งสาม model ได้คะแนนเท่ากัน หนึ่งในสามของ benchmark จึงแยก model เหล่านี้ออกจากกันไม่ได้ หมวดจัดหมวดหมู่ชนเพดานมากที่สุด (88 จาก 100 เคสทุก model ได้เต็ม)
3. **ป้ายความยากใช้ไม่ได้** Spearman ρ ระหว่างความยากที่ผู้เขียนกำหนดกับคะแนน: −0.026, −0.058, −0.100 คำว่า "ยาก" เป็นการคาดเดาของเรา ไม่ใช่สิ่งที่ model เจอจริง
4. **บันทึกคำตอบไม่ครบ** ผลที่วิเคราะห์เก็บคำตอบแค่ 80 ตัวอักษรแรก ผู้ตรวจจึงบางครั้งตัดสินไม่ได้ และให้คะแนนใหม่ไม่ได้ถ้าไม่รันใหม่ แก้ใน runner แล้วเมื่อ 2026-10-13 (เก็บคำตอบเต็ม, token, latency)
5. **รันรอบเดียวต่อ model** ด้วยค่าสุ่มเริ่มต้นของ provider จึงไม่มีการประมาณความแปรปรวนระหว่างรอบ
6. **กลุ่มย่อยเล็กและไม่สมดุล** (ภาษาถิ่น 3, ประชด 6, สำนวน 18) และมีแค่ 3 model ซึ่งทั้งหมดใช้ฟรีได้
7. **ผู้ตรวจคนเดียว** ไม่มีการวัดความเห็นตรงกันระหว่างผู้ตรวจ (inter-annotator agreement) และเฉลยของ 61 จาก 154 เคสที่ตรวจได้รับการยอมรับโดยไม่ได้ตรวจทีละเคส การตรวจซ่อนชื่อ model แต่สไตล์คำตอบอาจยังบอกได้ และ 129 จาก 462 คำตอบ (28%) ตัดสินไม่ได้เพราะถูกตัดเหลือ 80 ตัวอักษร โดยไม่เท่ากันในแต่ละ model (หัวข้อ 5.5)
8. **ข้อมูลหมดอายุเร็ว** เคสสแลงและข่าวล้าสมัยภายในไม่กี่เดือน ผลนี้อธิบาย model ณ เดือนตุลาคม 2569 เท่านั้น

## 8. งานในอนาคต (แนวทางต่อยอด)

1. **รันใหม่โดยเก็บคำตอบเต็ม** (ระบบรองรับแล้ว) และเพิ่ม latency/token รายเคส เพื่อนำต้นทุนมาเป็นแกนหนึ่งของการ routing
2. **แทนหรือเสริมการให้คะแนนด้วย keyword** ด้วย LLM ผู้ตัดสินแบบมีเกณฑ์ (rubric) โดยปรับเทียบกับการตรวจของคนบนชุด 154 เคส และรายงานความเห็นตรงกันระหว่าง LLM กับคน
3. **ตัดหรือทำให้เคสที่ชนเพดานยากขึ้น** และกำหนดความยากจากข้อมูลจริง (เช่น สัดส่วน model ที่ตอบผิด) แทนป้ายที่ผู้เขียนตั้ง
4. **เพิ่มเคสที่ต้องอาศัยความรู้วัฒนธรรม** เช่น ภาษาถิ่น การประชด สำนวน โดยใช้ผู้ตรวจหลายคน
5. **Fine-tuning (อยู่นอกขอบเขตโดยตั้งใจ)** paper นี้วัดว่า model พลาดตรงไหน ไม่ได้พยายามแก้ จึงไม่ได้เทรน model ใดเลย จุดที่พลาดซึ่งพบในงานนี้ ได้แก่ การอธิบายสแลง การแปลสำนวน และงานเขียนที่ใช้สแลงมาก เป็นเป้าหมายที่เหมาะสำหรับงานต่อยอดที่จะ fine-tune model เปิดขนาดเล็ก แล้วรัน benchmark และแบบฟอร์มตรวจชุดเดิมซ้ำเพื่อวัดผลที่เปลี่ยนไป รูปแบบข้อมูล ตัวตรวจข้อสอบรั่ว และตัวอย่างตั้งต้น 24 ตัวอย่างอยู่ใน `finetune/`
6. **เพิ่ม model** เช่น แบบเสียเงิน (`gemini-3.1-pro-preview`), model เฉพาะภาษาไทย (Typhoon, OpenThaiGPT) และ model ในเครื่องที่ใหญ่กว่า `qwen2.5:3b`
7. **Routing แบบเรียนรู้** ใช้คะแนนรายเคสจากงานนี้เป็นข้อมูลฝึก router แบบ RouteLLM ที่คำนึงถึงประเภทเนื้อหา
8. **กำหนดรอบปรับปรุงข้อมูล** เก็บข่าวและสแลงใหม่ทุก 6–12 เดือน

## 9. สรุป

งานนี้ถามว่า LLM แบบใช้ฟรีเชื่อถือได้แค่ไหนกับ prompt ภาษาไทยที่คำตอบขึ้นกับความรู้ทางวัฒนธรรม ไม่ใช่ข้อมูลที่ให้ไว้ในโจทย์ จาก 598 เคส Gemini 3.1 Flash-Lite ทำได้ดีกว่า gpt-oss ทั้งสองตัวในทุกหมวดและทุกระดับความยาก และเมื่อให้คนไทยตรวจคำตอบ 462 คำตอบแบบ blind ช่องว่างยิ่งกว้างขึ้น คือคำตอบที่ตัดสินได้ของ Gemini ถูกทั้งหมด เทียบกับ 76% ของ gpt-oss-120b และ 60% ของ gpt-oss-20b ความผิดพลาดกระจุกอยู่ที่สแลง การแปลสำนวน และงานเขียนที่ใช้สแลงมาก และเป็นคำตอบที่ลื่นไหลและมั่นใจ ทั้งการตรวจภาษาและตัวให้คะแนนแบบ keyword ของเรา (ซึ่งตรงกับคน 84% และให้ผ่าน 31 คำตอบที่ผิด) จึงจับไม่ได้อย่างน่าเชื่อถือ

ในทางปฏิบัติ หลักฐานนี้กลับสัญชาตญาณเรื่อง routing ของเรา ปัจจุบัน OpenPair ส่ง prompt ภาษาไทยทุกระดับไปที่ Gemini ตัวเล็กที่สุด แทนที่จะส่ง prompt ที่ยากกว่าไป model ที่ใหญ่กว่า ในเชิงวิธีการ หนึ่งในสามของ benchmark ชนเพดาน และป้ายความยากไม่สัมพันธ์กับคะแนน เราเผยแพร่ชุดเคส แบบฟอร์มตรวจ และสคริปต์วิเคราะห์ เพื่อให้งานต่อไปแทนการให้คะแนนด้วย keyword และทำเคสที่ชนเพดานให้ยากขึ้น และเพื่อให้งานที่จะพัฒนา model ให้เก่งขึ้น ซึ่งงานนี้ตั้งใจไม่ทำ เริ่มต้นจากแผนที่ที่วัดแล้วว่า model พลาดภาษาไทยตรงไหน
